# LogisticDigi — mobile (Phase 6)

Flutter companion to `apps/web`: the same operations console (Floor,
Approvals, Ledger) against the same Firestore project, for an operator who
needs to approve a payment away from a desk. It reads and writes exactly the
collections `firebase/firestore.rules` allows a client to touch — approvals
only, and only the four fields the rules accept while a request is pending.

## One-time setup

```bash
cd apps/mobile
flutter pub get

# Requires the Firebase CLI (`npm i -g firebase-tools`, `firebase login`)
dart pub global activate flutterfire_cli
flutterfire configure --project=logisticdigi
```

`flutterfire configure` registers Android/iOS apps against the `logisticdigi`
Firebase project and overwrites `lib/firebase_options.dart` (currently a
stub — see the comment at the top of that file). Until that command has run,
the app boots to a "Firebase is not configured" screen instead of crashing,
mirroring how `apps/web` handles a missing `.env.local`.

## Run

```bash
flutter run
```

## Release builds

`android/app/build.gradle.kts` reads signing credentials from
`android/key.properties`, which is gitignored along with the `.jks` keystore
itself — committing either would let anyone ship an update impersonating this
app. When that file is absent (a fresh clone, or CI that only builds debug),
the release build falls back to the debug key so `flutter build apk --debug`
and `flutter test` still work; it is not silently signed with a key anyone
can regenerate.

To build a real release on a new machine you need the keystore. It is not in
this repo by design — copy it from wherever the release machine backs it up,
then recreate `android/key.properties`:

```properties
storePassword=<...>
keyPassword=<...>
keyAlias=logisticdigi
storeFile=logisticdigi-release.jks
```

```bash
flutter build apk --release        # ~48MB, minified + resource-shrunk
flutter build appbundle --release  # for Play Store submission
```

**Never pass `--dart-define=EMULATOR_HOST=...` to a build you intend to
ship.** It compiles in a hard-coded emulator address, and the app will fail
at sign-in with `failed to connect to /127.0.0.1:9099` on any device that
isn't tunnelled to a developer's machine. A plain `--release` build leaves it
empty, which is the production behaviour.

## Publishing to Play Store

Done in this repo:

- App name `LogisticDigi`, package `com.logisticdigi.mobile`
- Adaptive launcher icon (foreground/background/monochrome) plus legacy and
  round variants, generated by `tool/make_icon.mjs` — edit that and re-run
  `node tool/make_icon.mjs` rather than hand-editing PNGs
- `playstore-icon-512.png`, the 512×512 listing asset Play requires
- `INTERNET` and `ACCESS_NETWORK_STATE` declared explicitly in the main
  manifest (the Flutter template only puts them in debug/profile, so a release
  build was getting them by accident via Firebase's merged manifests)
- Launch window painted the product's void black instead of the template white
- R8 minify + resource shrinking, release signing, all three ABIs in the bundle

Still to do in the Play Console, which cannot be done from here:

1. Create the app, upload `build/app/outputs/bundle/release/app-release.aab`
2. **Register the Play App Signing SHA-1 with Firebase.** Play re-signs your
   upload with its own key, so the fingerprint on the installed app is not the
   one in `key.properties`. Until you add it, Google Sign-In fails for every
   store install while working perfectly on your local builds — copy the SHA-1
   from Play Console → Setup → App signing, then follow the
   "SHA fingerprints" steps above.
3. Privacy policy URL, Data safety form (this app collects an email address
   and reads workspace data), content rating, store listing and screenshots
4. Bump `version:` in `pubspec.yaml` for every upload — Play rejects a
   duplicate versionCode

**If the keystore is ever lost, the app can never be updated on the Play
Store** — a new key means a new listing. Back it up somewhere other than this
machine.

### SHA fingerprints

Google Sign-In on Android will not work unless the signing certificate's SHA-1
is registered against the Firebase Android app *and* `google-services.json`
has been re-downloaded afterwards — the OAuth client entries the plugin reads
are generated by that registration, so a stale config file silently breaks
Google sign-in while email/password keeps working.

Both the debug and release fingerprints are already registered. To add another
(a new developer's debug key, or Play App Signing's key after your first
upload):

```bash
keytool -list -v -keystore <keystore> -alias <alias>   # copy the SHA1 and SHA256
firebase apps:android:sha:create 1:732824107426:android:1b50ff456f5f54df28dafb <SHA> --project logisticdigi
rm android/app/google-services.json
firebase apps:sdkconfig ANDROID 1:732824107426:android:1b50ff456f5f54df28dafb \
  --project logisticdigi --out android/app/google-services.json
```

Note that Play App Signing re-signs your upload with Google's own key, so
after the first Play submission you must register *that* SHA-1 too, or Google
Sign-In breaks for store installs while working fine on your local builds.

## Structure

- `lib/theme.dart` — the hazard/floor/paper palette, ported from
  `apps/web/src/app/globals.css`.
- `lib/models.dart`, `lib/live.dart` — Firestore document shapes and streams,
  ported from `apps/web/src/components/live.ts`. Money stays a string of
  minor units end to end, same as `packages/core/src/money.ts` — never a
  float.
- `lib/session.dart` — auth + custom-claim state, ported from
  `apps/web/src/lib/auth-context.tsx`.
- `lib/screens/` — Sign in, Floor, Approvals, Ledger, ported from
  `apps/web/src/app/sign-in` and `apps/web/src/app/operations/*`.

The map (`apps/web/src/app/operations/map`) and admin panel
(`apps/web/src/app/operations/admin`) are deliberately not ported: a 3D globe
and platform-owner kill switches are console tools, not something an operator
needs from a phone. Add them here if that assumption turns out wrong.
